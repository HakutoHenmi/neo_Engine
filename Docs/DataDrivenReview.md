# データドリブンへの置き換え

## 方針

確認課題「02_01 データドリブン」に沿って、**値だけが違い、処理内容は同じ**部分を、if else / switch / 三項演算子の連鎖からデータテーブルへ置き換えた。

- 1 つの対象 (行動・ステージ・形など) のデータは、構造体 1 つにまとめる。スライドの「ステージデータ構造体」と同じ考え方である。
- テーブルは enum の順に並べ、番号を添え字にして引く。範囲外の値は既定の行を返し、呼び出し側では分岐しない。
- コードに置く必要のないデータ (ステージの BGM) はファイル (`Resources/Data/*.json`) に置く。
- 名前と値の相互変換 (保存と読み込み) は、1 つの表を両方向から引く。

処理そのものが違う分岐 (部屋と輪の町の地形の作り方、タイトルメニューの選択後の処理など) は対象外とした。そうした分岐は、前回の課題で Strategy Pattern として整理している。

ゲームの数値・文言・保存形式は変更していない。期待値を置き換え前のコードの値にしたテストで確認している。

## 置き換えた箇所

### 1. スライムの変形 (体の行動) のデータ: `LifeActionTable`

一番効果の大きい箇所である。変形 1 つについてのデータが、6 ファイルの三項演算子の連鎖に分かれていた。

| データ | 置き換え前の場所 |
| --- | --- |
| 変形に必要な量 | `SlimeLifeRules.h` の `LifeRequiredMass` |
| 攻撃の長さ・ダメージ | `SlimeWeaponRules.h` の `LifeWeaponDuration` / `LifeWeaponDamage` |
| 流体の形の番号 | `SlimeLife.cpp` (8 段の三項演算子) |
| 未解放のときの案内 / 変形したときの案内 | `SlimeLife.cpp` (if else と、9 段・5 段の三項演算子) |
| HUD のアイコンと名前 | `SlimeDevour.cpp` |
| デバッグ表示の名前 | `SlimeDevTools.cpp` (switch) |

これを `LifeActionData` 構造体 (名前・必要な量・攻撃の長さ・ダメージ・形の番号・アイコン・案内) にまとめ、`LifeAction` の順のテーブル `LifeActionTable` にした (`Game/Chrono/SlimeLifeRules.h`)。

- 変形を追加するときは、enum とテーブルに 1 行足すだけでよい。以前は 6 ファイルの分岐をすべて直す必要があり、どれかを直し忘れると、案内だけ出ない・アイコンだけ違うといった見つけにくい不具合になっていた。
- 未解放の案内は `%d` に必要な量を入れる書式にした。ハンマー・剣・飛行機だけ別の処理をしていた if else もなくなった。
- 吸収モードでだけ文言が変わる案内 (ハンマー・タイヤ) は、`enterHintDevour` 列として持つ。
- ステージの変形アイテム → 変形 (`DevourItemForm`) と、変形 1 つだけの並び (`ChronoSystem::LifeForms`) も表から引く。

### 2. ステージのデータ: BGM と変形アイテムの名前

ステージのデータは、もともと `Resources/Data/devour_stages.json` から読む `DevourStage` 構造体の配列になっており、データドリブンだった。ただし BGM だけが `map == "ring" ? City : Battle` として、3 ファイル 3 か所のコードに残っていた。

- `devour_stages.json` の各ステージに `"music"` を追加し、`DevourStage::music` として読む。
- 曲名 → 曲の変換は、`music.json` の読み込みにも使っている曲名の表 (`Music::TrackNames`) を引く。
- 変形アイテムの名前 (`"tire"` など) の三項演算子も、名前とアイテムの組の表にした。

これでステージを足しても曲を変えても、コードは変更しない。

### 3. その他の値の表

| 対象 | 置き換え前 | 置き換え後 |
| --- | --- | --- |
| スライムの型の名前・得意・注意 | 3 つの関数の switch | `StyleText` の表 (1 行が型 1 つ) |
| こぼれた液体の物性 | 三項演算子で 3 つの定数を選択。散らす幅だけ `DevourSpill.cpp` に別の三項演算子 | `SpillKind` の順の表。散らす幅 `lane` も列に追加 |
| 部屋のギミックの道具の形 | 範囲・中の判定・芯の位置の 3 つの switch | `GimmickShapeData` (範囲・芯・判定関数) の表 |
| 吸収アニメーションの塊の種類 | 読み込みと保存で、逆向きの三項演算子の連鎖が 2 つ | 名前の表 1 つを両方向から引く |
| エンティティのタグ | `TagToString` の switch と `StringToTag` の if 列 | 名前の表 1 つを両方向から引く |
| 街の材質の色 | 21 個の case の switch | `CityMaterialId` の順の表 (補正色は、材質と色の組から作る表) |
| 描き文字の表示時間 | 同じ三項演算子が 2 か所 | 表 1 つ (`DevourPopLife`) |
| 輪の技の名前 | switch | 表 |
| ギミックの動き・パーティクルの放出形状の選択 (前回の Strategy) | switch | オブジェクトの表 |

## 検証

- Debug ソリューション全体: 警告 0 件・エラー 0 件でビルド成功。
- `tests/Run-DataDrivenTests.ps1` (新規): 置き換えた表から引いた値が、置き換え前の分岐に書かれていた値と一致することを確認する。対象は、変形ごとの量・攻撃の長さ・ダメージ・形の番号・アイコン・名前・案内の有無と文言、アイテム → 変形、型の文言、液体の物性と幅、塊の種類の名前の往復、技の名前、ギミックの形の値と範囲外の扱い。あわせて、表の行数と enum の数が一致することも確認する。
- `Run-DesignPatternTests.ps1`、`Run-EncapsulationTests.ps1`、`Run-ChronoTests.ps1`: 通過。
- `SlimeLifeRulesTests` (CPU のルールのテスト): 「bed stairs or cases are wrong」の 1 件だけ失敗する。部屋の地形 (`RoomRules.h`) の確認で、今回は変更していない。変更前のコミット (HEAD) のソースだけを取り出して同じテストを実行しても同じ 1 件が失敗するため、今回の変更による失敗ではない (11/08 以降の部屋の作り直しにテストが追いついていない)。

ゲーム画面での手動確認 (変形の案内・HUD のアイコン・ステージの BGM) は未実施。
